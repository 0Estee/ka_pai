# 制作卡牌

作者是**设计/策划，不写代码**。她给的输入是**手绘卡照片**或**口述**；
你交付的是**能装进 APK 里真的打出来的卡**。

一句话概括：**先看懂卡面 → 再判断引擎缺什么 → 然后才是写代码 → 最后一定要有测试和文档。**

---

## 0. 开工前记住三条

1. **卡面看不清就问，不能猜。** 数字空白、图标漏画、取整方向没写 —— 都要单独拎出来问作者，
   并给出你推荐的默认值。这里已经返工过。
2. **卡面上的词可能已经在词条表里，而且意思完全不同。** 见下面的「卡面排版约定」。
   这是整个流程里最容易出错的一步。
3. **一张卡的真正工作量在引擎，不在录数据。** 上一批 13 张卡里有 6 张需要新机制。
   先把第 2 步的判断做完，再动手。

---

## 1. 看懂卡面

### 1.1 手绘卡的排版是固定的

```
┌─────────────────────────┐
│ [图标]  卡名        ┌──┐│
│                     │③ ││  ← 右上角＝费用
├─────────────────────┴──┴┤
│                         │
│          插画            │
│                         │
│      ⚔2      ♥3         │  ← 左下＝攻击力  右下＝生命
├─────────────────────────┤
│      词条名（下划线）      │  ← 第一行：**已有的词条**，独占一行
│                         │
│   效果文本（可以好几行）   │  ← 下面几行：这张卡自己的效果
└─────────────────────────┘
```

左上角图标分两种：

| 图标 | 类型 | 引擎写法 |
|---|---|---|
| 剑 | 攻击性锦囊 | `type: 'spell'`, `spellKind: 'attack'` |
| 方块/盒子 | 道具性锦囊 | `type: 'spell'`, `spellKind: 'item'` |
| 人形 | 单位 | `type: 'unit'` |

### 1.2 下划线是词条标记，位置决定含义

- **独占一行** → 这是**本卡的词条**（如「水生」「狂热」）。去 `data/词条表.csv` 查，
  它十有八九**已经存在**，直接用那个 id，**不要新造一个同名的**。
- **出现在句子中间** → 是在**引用**一个已有词条（如拷问官的「扎根」）。

判定某个下划线行到底是词条还是效果，看**别的卡**：如果一张卡有词条行 + 效果行，
另一张卡只有效果行而效果完全一样，那说明**效果行是效果、词条行是词条**。
（上一批的对照：`鲨鱼` 是「水生 + 反伤效果」，`怨魂` 只有「反伤效果」——
所以反伤是效果，水生是地形词条。）

**如果你判断某个已有词条在卡面上被赋予了全新含义，先停下来问作者。**
改词条定义会影响所有带该词条的卡。

### 1.3 照片看不清就放大裁切，不要硬猜

原图通常 1440×1920，模型看到的预览会缩到 1134×1512，小字会糊。做法：

```powershell
Add-Type -AssemblyName System.Drawing
function Crop($inFile, $x, $y, $w, $h, $outFile, $scale) {
  $img = [System.Drawing.Image]::FromFile($inFile)
  $dst = New-Object System.Drawing.Bitmap ([int]($w*$scale)), ([int]($h*$scale))
  $g = [System.Drawing.Graphics]::FromImage($dst)
  $g.InterpolationMode = [System.Drawing.Drawing2D.InterpolationMode]::HighQualityBicubic
  $g.DrawImage($img, (New-Object System.Drawing.Rectangle 0,0,([int]($w*$scale)),([int]($h*$scale))),
               (New-Object System.Drawing.Rectangle $x,$y,$w,$h), [System.Drawing.GraphicsUnit]::Pixel)
  $g.Dispose(); $dst.Save($outFile, [System.Drawing.Imaging.ImageFormat]::Png); $dst.Dispose(); $img.Dispose()
}
# 文字框大致在 y 1180~1820、x 100~1350
Crop '原图.jpg' 100 1180 1250 640 '文字.png' 2
# 数值行（攻击/生命）单独再裁一次，位置大约 y 1010~1270
Crop '原图.jpg' 300 1010 800 260 '数值.png' 3
```

- 文字框：`y ≈ 1180`，高 `640`
- 数值行：`y ≈ 1010`，高 `260`
- 卡片**横着拍**的先旋转再裁。`RotateTransform(90)` 是顺时针；转出来倒着就换 `-90`。
- 裁完用 `read_image` 看，确认每一个数字和字。**没确认的数字不许写进代码。**
- 临时文件放 `.tmp-cards/`，做完删掉。

### 1.4 必须问作者的情况

| 情况 | 怎么问 |
|---|---|
| 数字位置空白 | 「这个数字卡面上是空的，按 N 录入可以吗？」 |
| 该画的图标没画（如只画了 ♥ 没画 ⚔） | 「攻击力没画，按 0 录入？还是漏画了？」 |
| 取整 / 舍入没写 | 「向上取整还是向下取整？我建议向上。」 |
| 范围没写（「场上」「敌人」指多大范围） | 给出 2 个候选口径让她选 |
| 顺序没说（「优先攻击」是结算顺序还是先制） | 给出候选含义让她选，并说明各自的强度影响 |
| 已有词条被赋予新含义 | 「这会让 X 词条变成全新效果，是要改词条，还是给这张卡的能力换个名字？」 |

问的时候**用 `ask_user_question` 一次问完**，每个都给推荐项。不要一条一条挤牙膏。

## 2. 判断引擎缺什么

对照 `data/词条表.csv` 和 `engine/README.md` 的动作/选择器表，把每张卡拆成：

- **纯数据** —— 已有词条 + 已有 op + 已有选择器就能表达 → 直接录
- **需要新机制** —— 缺词条 / 缺 op / 缺选择器 / 缺触发器 / 需要光环 / 需要国王被动

把「需要新机制」的清单先列出来。**先做这个判断，再动手写代码**，否则会边写边改结构。

具体每种机制往哪里加，见 [reference/引擎扩展指南.md](reference/引擎扩展指南.md)。

### 常见的新机制类型（按改动量从小到大）

| 类型 | 上一批的例子 | 改动量 |
|---|---|---|
| 新过滤器条件（`damaged` 等） | 斩杀「消灭一名受伤的敌人」 | 很小 |
| 新效果动作 op | 骨折「-2⚔-1♥」用 `modifyStats` | 小 |
| 新目标选择器 | 怨魂的「对其」用 `triggerVictim` | 中 |
| 新触发时机 | 「有敌人受到伤害时」观察者 | 中 |
| 新词条 | 先制 | 中 |
| 光环 | 拷问官、密命王牌 | 大 |
| 国王附着被动 | 战略纵深 | 大 |

## 3. 录入卡牌

卡牌定义全部加在 `engine/cards/user-cards.js` 的 `USER_CARDS` 数组末尾。
**id 接着往下排**（当前最后一张是 `U17`，下一张是 `U18`）。

```js
// ─────────────────────────────────────────────────────────
// 卡面：单位 / 「卡名」/ 费用 3 / 攻击2 生命3
//       词条行：狂热（下划线）
//       效果行：造成伤害:获得+1⚔+1♥
// 注：把「作者的裁决」「卡面空白处的取值」「为什么这么实现」都写在这里。
// ─────────────────────────────────────────────────────────
{
  id: 'U18',
  name: '卡名',
  type: 'unit',            // 'unit' | 'spell'
  cost: 3,
  atk: 2,
  hp: 3,
  keywords: ['frenzy'],    // 见 data/词条表.csv；带参写 'armor:1' 或 {id:'armor',x:1}
  text: '造成伤害:获得+1⚔+1♥',  // 卡面原文，界面直接显示；词条名不用重复写（已单独显示）
  effects: [               // 触发式异能
    { trigger: 'onDealDamage', actions: [ /* ... */ ] },
  ],
  auras: [ /* 光环，见引擎扩展指南 */ ],
}
```

锦囊用 `actions` 代替 `effects`：

```js
{
  id: 'U19', name: '斩杀', type: 'spell', spellKind: 'attack', cost: 2,
  text: '消灭一名受伤的敌人',
  actions: [
    { op: 'destroy', target: { kind: 'chosenEnemyUnit',
      filter: { damaged: true, spellTargetable: true },
      prompt: '选择一名受伤的敌人' } },
  ],
}
```

**每张卡上方的注释必须写卡面原文**，这样以后能核对「代码里的数值 == 卡面上写的数值」。

### 一个动作只能选一次目标

如果两个数值要同时作用在**同一个目标**上（骨折的 -2⚔ 和 -1♥），**必须用一个 `modifyStats`
动作**，不能拆成 `buffAtk` + `debuffMaxHp` —— 拆开玩家要点两次，AI 也会选错。

## 4. 补测试（这一步不能省）

测试在 `engine/test/smoke.mjs`，用现成的迷你框架：

```js
group('§11 第三批手绘卡（U18~U2x）');

test('「卡名」的效果一句话描述', () => {
  const state = game();                       // 默认 80 张填充牌库，不会触发牌库抽空
  const mine = deploy(state, 0, 'U18', 'mountain', 'front');
  const foe  = deploy(state, 1, 'W03', 'mountain', 'front');
  combat(state);                              // 触发开战结算
  assert.equal(foe.hp, 2);
});
```

现成的辅助函数：`game()` `give()` `deploy()` `cast()` `combat()` `nextTurn()` `at()` `king()`。

**每条新机制至少一个测试**，并且优先测这几类：

1. **边界**：目标不存在 / 目标满血 / 光环来源已离场 / 条件刚好不满足
2. **防死循环**：两个同类观察者同时在场，断言伤害次数是个确定的小数字
3. **对照**：新机制生效 vs 不生效的两个场景各一个测试（如「先制」和「无先制同时结算」）
4. **回归**：如果顺手修了老 bug，补一条能抓住它的测试

造对照卡时**往 `state.cardLib` 注入临时卡**，不要动正式的 demo 卡：

```js
state.cardLib.T44 = { id:'T44', name:'测试巨兽', type:'unit', cost:4, atk:4, hp:4, keywords:[] };
```

要直接破坏一个单位，用 `M.destroyUnit(state, unit, 'test')` + `G.flushTriggers(state)`
（测试文件里 `import * as M from '../src/mechanics.js'`）。

### 必须跑通

```bash
node engine/test/smoke.mjs      # 全绿才算数，当前 109 个
```

## 5. 重建与验证

```bash
node tools/build-web.mjs                                    # 打包成单文件 bundle
node tools/check-bundle.mjs                                 # DOM 集成测试（30 局自动对局）
powershell -ExecutionPolicy Bypass -File tools/build-apk.ps1
powershell -ExecutionPolicy Bypass -File tools/verify-apk.ps1
```

`build-apk.ps1` 自己会跑 smoke 和 check-bundle，任一失败就中止。

**改版本号**（每次加卡都该升一位）：`tools/build-apk.ps1` 的 `-VersionName`/`-VersionCode`、
`android/app/AndroidManifest.xml`、`tools/verify-apk.ps1` 里的 APK 路径、`README.md` 里的两处。

### 顺手做一次平衡自检

写个临时脚本跑 300 局自动对战，看三个数：

| 指标 | 健康范围 | 说明 |
|---|---|---|
| 先手胜率 | 45%~55% | 超出说明先后手严重失衡 |
| 平均回合数 | 7~10 | 太短说明快攻过强，太长说明僵持 |
| 牌库抽空收场比例 | < 40% | 太高说明对局不是「打到国王」而是「耗到没牌」 |

卡组大小用 `buildTestDeck(40)`（应用内的实际张数）。

## 7. 交付给作者时怎么说

作者不看代码，所以报告里要有：

1. **这次加了什么卡**（一张表：卡名/类型/费用/数值/效果）
2. **哪些卡需要新机制**，以及那个机制**改变了什么既有规则**（这是最需要她知道的）
3. **你自己定的边界**，单独列一张表 —— 每条写「我怎么处理的」+「为什么」+
   「想推翻的话改哪里」
4. **顺带修掉的老 bug**（如果有）
5. **APK 的路径 / 大小 / SHA256**

>  **产物不要往桌面（或仓库外任何地方）拷。**（作者 2026-10 明确要求）
> APK 一律留在仓库的 `dist/` 里，报告里给**路径 + 大小 + SHA256**就够了；
> 需要装到手机就用 `adb install -r <dist 里的路径>`，或用其它方式自己取。
> 桌面/下载目录是作者自己的地盘，往里写东西会污染她的工作区。

>  **每次改完都要提交并推到 GitHub。**（作者 2026-10 要求）
> 顺序固定：**跑门禁  `git add -A`  `git commit`  `git push`**，一条改动一个提交，别攒着。
> `build-apk.ps1`、`check-bundle.mjs`、`smoke.mjs` 是三道门禁，**红了不许提交**。
> 远端：`origin`（仓库地址见 `git remote -v`）。远端还没配时先问作者要地址。
> 提交信息写清「为什么改」作者靠它回溯；本仓库的 `docs/规则书-v0.2.md` 记规则口径、
> 提交历史记实现过程，两边都要留痕。
6. **平衡数据**（先手胜率、平均回合、牌库抽空比例），以及它的变化趋势
7. **请她重点试什么**（新机制里最不确定的那张）

含糊的地方**明说含糊**，不要为了让报告好看而假装确定。
