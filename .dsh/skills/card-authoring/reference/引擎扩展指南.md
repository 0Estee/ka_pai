# 引擎扩展指南

引擎是分层的，**改哪一层取决于你要加什么**。依赖方向单向，不能反向引用：

```
constants.js   线路 / 排 / 阶段 / 常量
    ↓
rng.js         确定性随机数
    ↓
keywords.js    词条层 —— 只做查询与判定，不改状态
    ↓
mechanics.js   机制层 —— 所有状态变更原语
    ↓
auras.js       光环层 —— 读取时叠加的持续影响
    ↓
effects.js     效果 DSL —— generator 解释器
    ↓
engine.js      状态机与公开 API
```

**状态只能由 `mechanics.js` 修改。** 这是硬规矩，便于审计。

下面按「你要加的东西」分类。

---

## 1. 新词条

**落点：`engine/src/keywords.js`**

1. `KEYWORD_DEFS` 加一项：

```js
先制: { name: '先制', params: false, kind: 'static', note: '开战时伤害先结算' },
```

字段含义：`name` 卡面名（`KEYWORD_BY_NAME` 会拿它反查 id）、`params` 是否带数值 X、
`kind` 类别（`trigger` / `replace` / `static` / `restrict` / `action`）、`note` 规则出处。

2. **实现判定**。词条层只允许写纯函数，例如：

```js
export function hasAmphibious(unit) { /* ... */ }
```

3. **如果需要改变既有流程**，改对应的那一处：

| 词条影响 | 改哪里 |
|---|---|
| 能否放在某线路 | `keywords.js` 的 `canPlaceInLane` |
| 受到伤害的修正 | `keywords.js` 的 `computeFinalDamage` |
| 攻击顺序 / 额外攻击 | `engine.js` 的 `resolveLane` |
| 攻击时的额外目标 | `engine.js` 的 `collectAttackEvents` |
| 造成伤害后的挂标记 | `mechanics.js` 的 `onDealtDamage` |

4. 补 `data/词条表.csv` 一行 + 规则书 §9 词条总表一行。

> 上一批的例子：`firstStrike`（先制）只影响 `resolveLane` —— 把拥有先制的单位
> 拆成独立的一批先结算，这一批的死亡在批次结束时就落地，所以被打死的敌人来不及反击。

## 2. 新效果动作（op）

**落点：`engine/src/effects.js` → `execAction` 的 `switch (action.op)`**

```js
case 'modifyStats': {
  const targets = yield* resolveTargets(state, ctx, action.target);
  for (const t of targets) {
    if (t.kind !== 'unit' || t.unit.removed) continue;
    if (action.atk) buffAtk(state, t.unit, action.atk);
    if (action.maxHp > 0) buffMaxHp(state, t.unit, action.maxHp);
    else if (action.maxHp < 0) debuffMaxHp(state, t.unit, -action.maxHp);
  }
  break;
}
```

规则：

- 改状态**一律走 `mechanics.js` 的函数**，不要在 `effects.js` 里直接写 `unit.hp -= n`
- 需要选目标就 `yield* resolveTargets(...)`（generator 会挂起等玩家回答）
- 未实现的机制**明确抛错**（参考 `move` / `bounce`），不要静默失败

**同时要改两处**，否则界面和 AI 会不知道这张牌在干什么：

| 文件 | 加什么 |
|---|---|
| `app/js/ui.js` → `spellDescription` | 一个 `case`，把 op 翻成人话（只在卡牌没写 `text` 时兜底） |
| `app/js/ai.js` → `scoreSpell` | 一个 `case`，给这个 op 估个分，否则 AI 会低估这张牌 |

## 3. 新目标选择器

**落点：`engine/src/effects.js` → `resolveTargets` 的 `switch (selector.kind)`**

分两类，**处理方式完全不同**：

### 3.1 需要玩家点选

在 `resolveTargets` 里 `yield { type: 'chooseUnit', options: [...] }`。
参考 `chosenEnemyUnit`。

还要同步改：

- `app/js/main.js` → `analyzeSpell`：算出可点的目标列表给界面高亮
- `app/js/ai.js` → `bestSpellTarget`：给 AI 一个选择策略

### 3.2 不需要玩家选择

比如 `ownKing`（自己的国王）、`allEnemyUnits`（敌方所有单位）、`triggerVictim`（触发事件里的受害者）。

**必须同时加到 `app/js/main.js` 的 `NO_CHOICE_TARGET_KINDS`**：

```js
const NO_CHOICE_TARGET_KINDS = new Set([
  'self', 'ownKing', 'enemyKing', 'allOwnUnits', 'allEnemyUnits', 'triggerVictim',
]);
```

漏了这一步的后果：`isPlayable` 会认为「这张牌没有可选目标」，于是**这张牌在手里永远灰着，
点了也打不出去**。上一批的「紧急包扎」「虫群」就踩过这个坑。

`app/js/ai.js` 的 `bestSpellTarget` 对不认识的选择器返回 `null`，
含义是「无需目标，直接打」—— 对这类选择器恰好是对的。

## 4. 新目标过滤器条件

**落点：`engine/src/keywords.js` → `matchesTargetFilter`**

```js
// 「受伤」= 当前生命低于生命上限
const hurt = unit.hp < unit.maxHp;
if (filter.damaged !== undefined && hurt !== !!filter.damaged) return false;
```

**这个函数有三处调用方，必须保持一致：**

| 文件 | 用途 |
|---|---|
| `engine/src/effects.js` | 引擎自己校验（**引擎是最终权威**，界面/AI 的 bug 不能让它生效） |
| `app/js/main.js` → `analyzeSpell` | 界面高亮 |
| `app/js/ai.js` → `bestSpellTarget` | AI 决策 |

三处都要传同一个上下文：

```js
matchesTargetFilter(unit, filter, filterCtx(state))
```

### 需要看全局才知道的条件，走 ctx

有些条件光看单位自身看不出来 —— 比如「扎根」可能是拷问官**光环授予**的。
这时用 `filterCtx(state)` 注入：

```js
export function filterCtx(state) {
  return {
    atkOf: (u) => effectiveAtk(state, u),   // 有效攻击力（含光环）
    isRooted: (u) => hasRooted(state, u),   // 含光环授予的扎根
  };
}
```

`matchesTargetFilter` 里对应写成 `ctx.atkOf ? ctx.atkOf(unit) : unit.atk`，
不传 ctx 时退化读裸数值。

## 5. 新触发器

**落点：入队在 `engine/src/mechanics.js`，执行无需改 `engine.js`。**

### 5.1 入队

```js
export function queueTrigger(state, unit, triggerName, payload = {}) {
  state.triggerQueue.push({ unit, triggerName, payload });
}
```

在合适的时机调用它。已有调用点：

| trigger | 调用点 |
|---|---|
| `onPlay` | `engine.js` 的 `playCard` / `apiFor().summonToken` |
| `onDeath` | `mechanics.js` 的 `destroyUnit` |
| `onDealDamage` | `mechanics.js` 的 `onDealtDamage` |
| `onEnemyDamaged` | `mechanics.js` 的 `notifyDamageWatchers` |
| `onFriendlyUnitDestroyed` | `mechanics.js` 的 `destroyUnit`（走国王队列） |

`payload` 会原样变成效果执行时的 `ctx.payload`，配合一个选择器把「触发事件里的那个东西」
交给动作。比如怨魂：

```js
// mechanics.js：敌方单位掉血 → 通知所有观察者
queueTrigger(state, watcher, 'onEnemyDamaged', { victim });
// effects.js：选择器 'triggerVictim' 从 ctx.payload.victim 取
```

### 5.2 执行

`engine.js` 的 `runTriggeredEffects` 已经按 `trigger` 名过滤，**新触发器不用改它**。

### 5.3 防死循环（必做）

如果新触发器**自己会造成伤害**，必须在 `runTriggeredEffects` 里加护栏：

```js
noKeywordsForDamage: triggerName === 'onDealDamage',
noWatchersForDamage: triggerName === 'onEnemyDamaged',
```

否则「造成伤害: 对敌方单位造成1点伤害」会自己触发自己，无限递归。
**并且一定要写一个测试断言伤害次数是个确定的小数字**，不能只靠肉眼看代码。

### 5.4 别忘了

规则书 §1 的「异能的发动时机标注」表加一行。

## 6. 光环

**落点：`engine/src/auras.js` + 卡牌定义的 `auras` 字段**

### 6.1 铁律：光环不能直接改 `unit.atk`

永久加成（吸血鬼的 +1/+1）直接写进 `unit.atk` 就对了 —— 它一旦获得就不会消失。

光环不一样：拷问官一死，-3 攻必须立刻消失；密命王牌旁边一有队友，+3 攻必须立刻消失。
如果也直接改数值，就得在**每次棋盘变动时**「撤销上一次、再重新加上」，
漏掉任何一个时机就会留下永久错值。

所以采取**读取时计算**：`unit.atk` 永远只存永久值，需要真实数值时调：

```js
effectiveAtk(state, unit)   // = max(0, unit.atk + 光环修正)
```

棋盘最多 8 个单位，重复计算的开销可以忽略。

### 6.2 加一个新光环

卡牌定义上：

```js
auras: [
  { kind: 'buffAtk', amount: -3, to: 'rootedEnemies' },
  { kind: 'buffAtk', amount: 3, to: 'self', condition: 'noOtherAllies' },
  { kind: 'grantKeyword', keyword: 'rooted', to: 'laneEnemies' },
]
```

`kind` 有 `buffAtk` / `grantKeyword`；`to` 有 `self` / `laneEnemies` / `rootedEnemies`。

要加新的 `to` 或 `condition`，改 `auras.js` 的 `appliesTo` / `conditionMet`，
并在 `engine/README.md` 的光环表里登记。

### 6.3 授予类光环的递归陷阱

「给敌人扎根」和「扎根的敌人减攻」这两条如果互相依赖，会无限递归。
所以 `rootedSet` 里禁止授予类光环用 `rootedEnemies` 作对象（引擎会直接抛错），
并且**先算出一个 `rootedSet` 集合**，再拿它去判减攻。

### 6.4 所有读攻击力的地方都要改成 `effectiveAtk`

这是最容易漏的一步。改完 grep 一遍 `.atk`：

| 位置 | 说明 |
|---|---|
| `engine.js` → `resolveLane` 的 `u.atk > 0` 过滤 | 被减到 0 攻的单位不该攻击 |
| `engine.js` → `collectAttackEvents` | **伤害数值**来源 |
| `engine.js` → `describeUnit` / `renderBoard` | 界面与调试显示 |
| `app/js/ui.js` → `unitHTML` | 棋盘上的单位卡片 |
| `app/js/ai.js` → `threatOf` | AI 的威胁评估 |

**漏掉的症状**：界面显示 5 攻，实际打出来是 2。测试里要专门断言一个
「光环改变后的有效攻击力真的用于伤害计算」（参考「密命王牌单独在场时打出的是 6 点伤害」）。

## 7. 国王附着被动

**落点：`engine.js` 的 `makePlayer` + `mechanics.js` + `effects.js`**

1. `makePlayer` 里初始化 `kingEffects: []`
2. 附着效果用 `attachKingEffect` op（`effects.js` 的 `execAction`）
3. 入队用 `mechanics.js` 的 `queueKingTrigger(state, side, triggerName, payload)`
4. 执行走 `engine.js` 的 `runKingTriggeredEffects`，`flushTriggers` 会按 `kingSide` 自动分流
5. 触发时机由 `mechanics.js` 里别的函数调用 `queueKingTrigger` 决定
   （如 `destroyUnit` 里的 `onFriendlyUnitDestroyed`）

一个国王可以有多个同类被动（打两张战略纵深 = 每次死单位抽两张）。

## 8. 平衡自检脚本

写成临时 `.mjs` 跑完删掉。卡组用 `buildTestDeck(40)`（应用内实际张数）。

```js
import * as G from "./engine/src/engine.js";
import { TEST_CARD_LIB, buildTestDeck } from "./engine/cards/test-cards.js";

function mul(a){return function(){a|=0;a=a+0x6D2B79F5|0;let t=Math.imul(a^a>>>15,1|a);
  t=t+Math.imul(t^t>>>7,61|t)^t;return((t^t>>>14)>>>0)/4294967296;};}

const N = 300, size = 40;
const tally = {0:0, 1:0, draw:0}; let turns = 0, deckOut = 0;
for (let seed = 1; seed <= N; seed++) {
  const s = G.createGame({ seed, firstPlayer: seed % 2, deck: buildTestDeck(size), cardLib: TEST_CARD_LIB });
  G.startGame(s);
  const r = mul(seed * 7919); let g = 0;
  while (!G.isOver(s)) {
    if (++g > 4000) throw new Error(`种子 ${seed} 不收敛`);
    const a = G.getActor(s);
    if (a === null) { G.advance(s); continue; }
    const p = G.getLegalPlays(s, a);
    if (!p.length) { G.advance(s); continue; }
    const c = p[Math.floor(r() * p.length)];
    const pl = c.places[Math.floor(r() * c.places.length)];
    try { G.playCard(s, a, c.iid, pl ? { lane: pl.lane, row: pl.row } : {}); }
    catch { G.advance(s); }
  }
  tally[s.winner]++; turns += s.turn;
  if (/牌库抽空/.test(s.winReason || "")) deckOut++;
}
console.log(`卡组 ${size} 张: 先手胜率 ${(tally[0]/N*100).toFixed(1)}%  `
  + `平均回合 ${(turns/N).toFixed(1)}  牌库抽空收场 ${deckOut}/${N}`);
```

**和上一版对比**，报告变化趋势，而不是只报绝对值。
