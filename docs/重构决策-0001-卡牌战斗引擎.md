# 重构决策 0001 · 卡牌战斗引擎（Card Combat Engine）去留

- 日期：2026-11-07
- 状态：**已裁决 —— 不采用，降级为参考代码**
- 涉及：`third_party/card_combat`（原 `addons/card_combat`、`godot/addons/card_combat`）、`godot/project.godot`、`godot/scripts/engine/kp_game.gd`

## 一、当初为什么引进

2026-11-01 的迁移把「手机端改用 Godot + Card Combat Engine」当作目标，于是在工程里
vendor 了一份 CCE（v1.1.1，26 个脚本 / 6068 行，AGPLv3 或商业双授权），打算用它做
「战斗外壳」—— 即：开战结算、伤害管线、触发器队列这些通用部分交给它，游戏层只提供
卡牌数据和异能回调。

## 二、查到的实际情况

1. **它一次都没被用上。** 全仓库对 `card_combat` / `CombatSession` / `Combatant` /
   `CombatResolver` 的引用只出现在 CCE 自己的文件里；`kp_game.gd`（5489 行）自己实现了
   开战结算（§11 `run_combat` / `resolve_lane` / `apply_attack_batch`）、伤害管线（§4）
   和触发队列（§10）。也就是说它是个**纯死重**。
2. **两处重复拷贝**：`addons/card_combat` 与 `godot/addons/card_combat` 内容逐字节相同
   （仅前者多 `LICENSE_CCE` 与 `llms.txt`），后者会被 Godot 编译进工程。
3. **它的战场模型对不上本作。** CCE 是「hero + 若干 pair（attacker/defender）」的一维
   交战模型；本作是 **4 条线路 × 前/后排 × 7 个阶段 × 国王 20 血**，另有光环、词条、
   埋伏陷阱、超能力、炼金/异火堆、强化精通等 200+ 条裁决细节。要接上去，等于把 CCE 的
   `CombatPair/CombatSession` 全部改造一遍 —— 改造量比 `kp_game.gd` 已经写完的还大。
4. **规则等价已经用对拍证明了。** `tools/parity/js-run.mjs` + `godot/tests/parity.gd`
   用同种子同牌库重放同一串动作，12 个种子 901 步**逐字节一致**（含 rng 状态、手牌顺序、
   牌库顶三张、场上每格攻血）。这是本作真正的资产：一份与 229 条 JS 回归测试对得上的
   GDScript 引擎。
5. **授权污染。** CCE 是 AGPLv3（或商业授权）。AGPL 的传染性覆盖「与之结合的作品」，
   一旦真接进来，整个游戏（含要上架的 APK 与联机服务端）都要按 AGPL 开源。本作目前的
   发行方式是自建 APK + Cloudflare 联机，没有准备开源全部源码。

## 三、裁决

**不采用 CCE。** 具体动作：

- 只保留一份拷贝，挪到项目外的 `third_party/card_combat/`（含 `LICENSE_CCE`、
  `LICENSE`），**不进 Godot 工程、不参与构建、不打进 APK**；
- 删掉 `godot/addons/card_combat` 与根目录 `addons/card_combat`；
- `godot/project.godot` 头部注释同步改正（原来写着「战斗外壳使用 addons/card_combat」，不实）。

保留一份的理由：它的 `combat_trigger_queue.gd`（触发器排队与结算时序）与
`combat_event.gd`（事件流）设计得比本作清晰，写战斗演出动画时值得借鉴**思路**（不抄代码）。

## 四、如果你要推翻这个裁决（怎么回退）

代价清单，先看清楚再动手：

1. 授权：整个客户端 + 服务端按 AGPLv3 开源，或向作者买商业授权；
2. 改造面积：`kp_game.gd` §11 开战结算、§4 伤害管线、§10 触发队列三个分节要重写成
   CCE 的 `CombatSession` 驱动，卡牌 DSL 的 `effects/actions` 要翻译成 CCE 的
   `ability_fn` 回调 —— 这部分是全项目最密集的规则代码；
3. **对拍会失效**：`godot/tests/parity.gd` 守的是「与 JS 版逐字节等价」，换成 CCE 的
   结算顺序后这条底线没了，等于放弃已经建立的回归保护；
4. 需要重做的验证：229 条 JS 断言的对应版本要重新在 Godot 侧建立。

如果只是想要 CCE 的「动画事件流」，第 5 节的做法更划算：在 `kp_game.gd` 现有的
`log_event` 之上加一层事件订阅（UI 已经这样接），不需要引第三方框架。

## 五、替代方案（推荐）

- **规则**：`godot/scripts/engine/kp_game.gd`（已有，对拍守住）
- **演出**：复用 `state.log` 与 `state_changed` 信号，UI 层（`scripts/ui/`）做时间轴播放；
  事件粒度不够就扩充 `log_event`，不要引入框架
- **AI**：`godot/scripts/ai/kp_ai.gd`（由 `app/js/ai.js` 移植，见 #0002）
