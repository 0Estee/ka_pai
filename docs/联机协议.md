# 局域网联机协议 v2

> **v2 变更**：收消息默认走 **WebSocket**（新增 §2.7），长轮询保留为回落路径；
> 新增**手动连接**兜底（§2.8），解决「UDP 广播被路由器拦掉导致搜不到房间」。
> 发送路径（/api/send）与锁步逻辑**完全没变**。

> 本文是 **Java 层（服务端）** 与 **JS 层（客户端）** 之间唯一的契约。
> 两边都按这份文档实现，改协议必须先改这里。

---

## 0. 核心思路

引擎是**完全确定性**的：所有随机数来自 `state.rng`（由种子决定），
AI 唯一的随机项也是 `state.rng.state`，没有用过 `Math.random`。

所以联机**不需要同步棋盘，只需要同步操作**：

```
主机：createGame(seed, deck)  →  双方各自跑同一个引擎
主机出牌  →  广播 { playCard }  →  两端各执行一次  →  状态保持一致
客人出牌  →  广播 { playCard }  →  两端各执行一次  →  状态保持一致
```

这跟「回放」是同一件事 —— `app/js/replay.js` 里那套操作日志，
换个传输层就是联机协议。

**乐观锁步（lockstep）**：任何一方都可以算，但只有轮到自己时才允许发出操作。
每 N 步互相校验一次状态指纹，一旦不一致立刻中止并提示（而不是各自跑飞）。

## 1. 谁提供页面

**页面由主机的 HTTP 服务提供**，两端都从它加载 App。

| | 打开的地址 | 同源？ |
|---|---|---|
| 主机 | `http://127.0.0.1:8765/?net=host&room=房间名` | ✅ |
| 客人 | `http://192.168.x.x:8765/?net=guest&room=房间名` | ✅ |

为什么必须这样（而不是「两端都跑 APK，客人去连主机的 API」）：

1. **CORS**：APK 里的页面是 `file://` 源。从 `file://` 发 `fetch` 到 `http://`
   会被 WebView 的 `setAllowUniversalAccessFromFileURLs`（默认关闭）直接拦掉，
   加 `Access-Control-Allow-Origin` 也没用。让页面**从 HTTP 加载**就绕开了整个问题。
2. **版本一致**：两端跑的是同一套前端资源（`dist/` 整目录由主机下发），
   不会出现「一边是新版一边是旧版」导致的操作流不一致。

代价：客人必须先装 APK（用来扫描房间），扫到之后 WebView 导航到主机。
**App 本身的资产仍然来自 APK**，所以扫描阶段不依赖网络。

## 2. HTTP 接口

服务端口默认 **8765**（被占用时往上找，最多试 10 个）。

### 2.1 静态资源

| 路径 | 内容 |
|---|---|
| `/` `/index.html` | `assets/index.html` |
| `/style.css` | `assets/style.css` |
| `/screens.css` | `assets/screens.css` |
| `/dist/bundle.js` | `assets/dist/bundle.js` —— **加载器**，按顺序插入下面那些脚本 |
| `/dist/modules/*.js` | `assets/dist/modules/*.js` —— 前端真正的代码，**一个源文件一个脚本**（36 个） |

> `dist/` 现在是「1 个加载器 + 36 个模块脚本」。`bundle.js` 仍然存在，是因为
> `index.html` 只引它、而且它是本表里 Java 侧测试断言过的那条路径；
> 它本身只有 2 KB，作用是用 `document.write` 把 `dist/modules/` 按依赖顺序插进页面
> （解析期插入是同步有序的，所以不能用 `type="module"` —— file:// 下会被 CORS 挡掉）。
> 静态资源是**按路径通用读取**的，所以新增 `dist/` 下的文件不需要改 Java 代码。

**任何其它非 `/api/` 路径都返回 index.html**（单页应用兜底）。

响应头必须包含：

```
Content-Type: text/html; charset=utf-8   （.css → text/css，.js → application/javascript）
Cache-Control: no-store
Access-Control-Allow-Origin: *
```

### 2.2 房间信息

```
GET /api/room
→ 200 {"ok":true,"room":"房间名","host":"张三","port":8765,"players":2,"started":false,"version":1}
```

### 2.3 发消息

```
POST /api/send?who=host|guest&name=<显示名>
Body: 任意 JSON（就是一条消息，见 §3）
→ 200 {"ok":true,"seq":<该消息的序号，从 0 开始>}
```

### 2.4 收消息（长轮询）

```
GET /api/poll?who=host|guest&since=<N>&timeout=20000
→ 200 {"ok":true,"now":<当前总消息数>,"msgs":[{"seq":N,"from":"host","name":"张三","msg":{...}},...]}
```

- `since=N` 表示「我已经处理到第 N-1 条」，返回 `seq >= N` 的全部消息。
- 没有新消息时**挂起最多 `timeout` 毫秒**再返回空数组（长轮询，避免空转）。
- `timeout` 上限 30000，默认 20000。
- 一方离开后，另一方下一次 poll 要立刻返回 `{"ok":false,"error":"peer-left"}`。

### 2.5 离开

```
POST /api/leave?who=host|guest
POST /api/start?who=host          主机开始游戏，房间进入 started 状态
```

### 2.6 健康检查

```
GET /api/health → 200 {"ok":true,"version":1}
```

## 3. 消息格式（放在 `/api/send` 的 body 里）

所有消息都是 `{"t":"类型", ...}`。

| `t` | 方向 | 字段 | 说明 |
|---|---|---|---|
| `hello` | 双向 | `name` | 刚连上时报名字 |
| `lobby` | 主机→客人 | `room`, `host` | 房间状态变化 |
| `start` | 主机→客人 | `seed`, `firstPlayer`, `deck`, `hostSide`, `factions` | 开始游戏。`deck` 是卡牌 id 数组；`factions` 是 `[主机阵营, 客人阵营]`（缺省空数组 = 没有阵营，两份引擎都必须拿到同一个值，否则抽牌不一致） |
| `act` | 双向 | `a` | 一条引擎操作，见 §4 |
| `hash` | 双向 | `step`, `h` | 状态指纹，用于校验一致性 |
| `bye` | 双向 | `reason` | 主动退出 |
| `ping` | 双向 | — | 保活 |

## 4. `act` 里的引擎操作

延续 `app/js/replay.js` 里的操作格式，**完全一致**：

```js
{ k: 'a' }                                    // G.advance(state)
{ k: 'p', s: 0|1, i: <iid>, o: {...} }        // G.playCard(state, s, i, o)
{ k: 'c', v: <choice> }                       // G.resolveChoice(state, v)
{ k: 'x', s: 0|1, u: <uid> }                  // G.sacrificeUnit(state, s, u)（恶魔阵营的献祭按钮）
```

`o` 只允许 `lane` / `row` / `targetUid` / `targetKing`。

### 4.1 效果中途要选目标时，由哪一侧来点？

有些牌打出后还要选东西（「抉择」、`chooseEnemyTarget`、开战选攻击目标）。引擎会把这
类请求**挂起**，并且每个请求都自带一个 `side`  该做主的那一方。

- **只有 `side` 等于自己那一侧的那台设备能作答**；另一侧显示「等待对手选择」，
  连选项都不列出来（选项里可能带着对手的手牌和目标）。
- 答案还是走锁步：`{ k: 'c', v: <choice> }`。对方的设备收到后 `G.resolveChoice`，
  和本地作答是同一条路径。
- 谁也不能替对手答：两台设备同时能点的话，先点的那个就替对手做了决定。
- **联机不开 `autoResolveChoices`**（`Session.applyStart` 里设成 `false`）。开着的话
  挂起的请求会被「取第一个选项」静默答掉，等于把真人当 AI。
- 单机不受影响：没有会话时，这一问就恒归本地。

## 5. 状态指纹

为了避免「两端悄悄跑飞」，每执行 8 步操作就互发一次指纹。

`hash` = 把下面这些字段拼成字符串后取 32 位 FNV-1a：

```
turn | phase | winner | kingHp0 | kingHp1 | 手牌张数 | 棋盘快照
```

棋盘快照按 `线路顺序 → 双方(0,1) → 排(front,back)`，每个格子拼
`cardId:atk:hp:maxHp`，空格用 `-`。

**两端算法必须逐字节一致**，所以它写在 `app/js/multiplayer.js` 的
`stateHash(state)` 里，Java 层不参与。

不一致时：立刻停止接受操作，界面提示「与对手的进度不一致，已中止」，
并给出结束时的回放（回放里能看到分歧发生在第几步）。

## 6. UDP 房间发现

主机的 HTTP 服务起来之后，同时监听 **UDP 8766** 用于被发现。

### 探测

客人向 `255.255.255.255:8766` 以及**每个网卡的广播地址**发送：

```
KAPAI_DISCOVER/1
```

（只发广播地址，不做全网段扫描 —— 那太慢且容易被防火墙拦。）

### 应答

主机收到后**单播**回客人：

```json
{"t":"room","room":"房间名","host":"张三","ip":"192.168.1.5","port":8765,"players":1,"started":false,"version":1}
```

### 规则

- 服务只在**主机**侧启动；客人侧只发送探测、只接收应答。
- 客人等待 **1500ms** 收集应答，按 `ip:port` 去重。
- 主机进入游戏后 `started=true`，客人列表里显示「已开始」且不可加入。
- 主机关闭房间/退出时停掉 UDP 监听，否则列表里会残留死房间。
- **广播地址要计算**：`NetworkInterface.getInterfaceAddresses()` 里的
  `getBroadcast()`；不要只发 `255.255.255.255`（部分路由器/手机会丢）。

## 7. 掉线处理

| 情况 | 行为 |
|---|---|
| 长轮询连续失败 | 界面显示「与对手的连接中断」，进入**等待重连**状态 |
| 等待重连 | 每 2 秒重试一次，最长 **60 秒**；期间棋盘冻结、禁止操作 |
| 重连成功 | 拉取 `since=` 之后的所有消息补齐，然后校验指纹；一致就继续 |
| 超过 60 秒 | 判掉线方失败，走正常的结算流程（发金币、存回放） |
| 主动退出（点「退出」） | 立刻发 `bye`，对方收到后按掉线处理但**不等待**，直接结算 |

**主机掉线 = 房间消失**，客人无法重连，直接判负。
这一点要在界面上说清楚：主机不能中途退出。

## 8. 谁负责推进自动阶段

引擎里 `getActor(state) === null` 的阶段（回合开始 / 开战 / 回合结束）是自动的。

**只有主机推进这些阶段**，并把 `{k:'a'}` 广播出去；客人只等待、只应用。

否则两端会各推一次，回合数直接翻倍。

判断方式：`if (net.isHost() && G.getActor(state) === null) advanceGame();`

## 2.7 WebSocket 推送通道（收消息的首选路径）

**长轮询仍然保留**，但默认走 WebSocket。

```
GET /ws?who=host|guest&since=<seq>     ← 升级为 WebSocket（101）
```

握手之后服务端**只做一件事**：把新出现的消息推给这一端。
**发送仍然走 `POST /api/send`** —— 这样发送路径完全没变，已有的错误处理与测试继续有效。

| 项 | 长轮询 `/api/poll` | WebSocket `/ws` |
|---|---|---|
| 送达延迟 | 服务端一有消息就回（也很快） | 立即推 |
| 每条消息的开销 | 一次完整的 HTTP 请求/响应 | 一个几字节的帧头 |
| 断线时多久知道 | 下一次轮询失败 | 立刻（socket 关闭 / ping 超时） |
| 挂着空闲连接 | 一个 20 秒的 HTTP 连接，部分路由器/WebView 会掐 | 常连接 + 20 秒一次 ping 保活 |

### 只推「对方」发的消息

服务端**不把自己发的消息推回给发送方**。本地操作已经执行过一次，
推回去会再执行一遍。JS 侧也有一层同样的过滤，但那是兜底，正确性由服务端保证
（这条是桌面测试抓出来的：一开始服务端把 `from=guest` 的消息也推给了 guest）。

### 双方各自实现的责任

- **服务端**：握手（`Sec-WebSocket-Accept` = base64(sha1(key + GUID))）、写文本帧（不加掩码）、
  读客户端帧（**要解掩码**）、ping/pong、close。
  **没实现**：分片消息、二进制帧、扩展（permessage-deflate）—— 用不上。
- **客户端**：先试 `/ws`，**4 秒内连不上就回落到长轮询**。
  为什么两条路都留：客人是从主机的服务加载页面的，而主机可能还是**旧版 APK**、
  没有 `/ws`；也可能被中间设备挡掉。连不上就退回旧路径，
  最差情况等于改造前的行为，不会因为换传输层而彻底连不上。

### 新增的容错点

- 服务端每一端的推送通道只保留**一条**，重复连接会顶掉旧的（否则重连会变成两个通道同时推）。
- 服务端每 20 秒发一次 ping；客户端在 READER 线程里应答，
  这样对端拔网线也能在秒级发现，而不是等到 TCP 写失败（那可能要几分钟）。

## 2.8 手动连接（扫描不到房间时的兜底）

UDP 广播在很多常见环境下会被拦掉：路由器的 **AP 隔离**、访客网络、企业 Wi-Fi、
以及部分手机的省电策略。表现就是**扫描永远是空的**，但两台设备其实在同一网段。

所以加入房间的界面上**一直有一个手动输入框**：

```
让主机把大厅里显示的那串地址念给你，填在这里：  [192.168.1.7:8765]  [手动连接]
```

- 主机大厅里本来就已经显示了 `http://<本机IP>:<端口>/`（协议 §1 的 `joinUrl`）。
- 输入会被规范化：`192.168.1.7`、`192.168.1.7:8765`、`http://192.168.1.7:8765/`
  都认；端口不写就按默认 **8765**。
- 校验失败**在界面上就地报错**，不能静默失败 ——
  WebView 里 `alert` / `prompt` 是**静默失效**的（什么都不发生），这也是为什么用内嵌输入框而不是 `prompt()`。

## 9. 不做的事（v1 明确排除）

| 项 | 原因 |
|---|---|
| 断线后 AI 接管 | 两端可能算出不同结果，需要额外的一致性机制，v1 不值得 |
| 房间名自定义 / 密码 | 局域网内够用，先不做 |
| 观战 | 需要第三种角色，v1 不做 |
| 互联网联机 | 需要中继服务器，不在本次范围 |
| 版本协商 | 页面由主机提供，天然同版本 |
